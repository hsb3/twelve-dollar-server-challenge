# Security review: swift-iouring-akbashev

## Verdict
Safe to build and run. Nothing malicious or blocker-level was found. The server is a single-threaded Swift io_uring HTTP/1.1 server (raw `io_uring_*` system calls, no liburing) over the unmodified SQLite 3.54.1 amalgamation, plus one checkpointer thread. At runtime it reads only the four spec env vars and a handful of optional tuning knobs. It touches only its listening sockets, the accepted connections (as io_uring direct descriptors), two eventfds, stderr, and the SQLite file at SQLITE_PATH with its -wal sibling (the `unix-excl` VFS keeps the WAL index in memory, so there is no -shm file). It makes no outbound connections, spawns no processes and reads no credentials. It has no third-party packages: Package.swift declares no dependencies and there is no Package.resolved. The Swift 6.4.2 tarball's sha256 matches install.sh and carries a good signature from the Swift 6.x release key. The SQLite zip's sha256 matches build.sh, its SHA3-256 matches sqlite.org's download page, and the extracted sqlite3.c matches the SHA3-256 in the 3.54.1 release log.

`seccomp: unconfined` is justified. start.sh runs the binary with no flags. `Reactor.run()` (`Reactor.swift:82-87`) calls `addRing()`, and a failed `io_uring_setup` throws to `fatalError` there. No epoll or other fallback exists, and no env var or flag selects one. The README says so too ("io_uring must be allowed: Docker's default seccomp profile blocks it"). The code's io_uring use is limited to multishot accept into direct descriptors, multishot and single receives into provided buffers, send, shutdown, close, async cancel, and one READ opcode on the checkpointer's own eventfd. It uses no OpenAt, Connect, Splice or file-path opcodes, and the only plain descriptor any opcode targets is that eventfd.

What "unconfined" exposes: the whole server container, including nginx and the entrypoint, runs without Docker's syscall filter. That widens the kernel attack surface, and io_uring has a history of local privilege-escalation CVEs. On Docker Desktop for Mac the exposed kernel is the LinuxKit VM's, not macOS. The compose file still sets `no-new-privileges`, Docker's default capability drop and resource limits, and the server runs as `ubuntu` via setpriv. This is acceptable for code that, as reviewed, does nothing hostile.

## Findings
- **note** `install.sh:20-32`: the tarball is unpacked as root before its hash is known. curl pipes through `tee -p "$FIFO"` into `tar -xz` under /opt/swift while a background `sha256sum` reads the FIFO. The hash is compared only after `wait`, and on a mismatch `/opt/swift` is deleted and the install fails. The check covers the whole download (`tee -p` keeps feeding the FIFO even if tar stops reading early), it fails closed if curl, tar or sha256sum fails (`set -euo pipefail`; an empty `.sum` is a mismatch), and nothing from /opt/swift runs before the comparison. The residual risk is that unverified archive contents are written to disk as root (GNU tar keeps owners and modes for root and guards against `..` and absolute-symlink escapes) for the length of the download. The source is official HTTPS, and the bytes I fetched match the pin and the Swift signature, so this is acceptable. Verify-then-extract would be stricter. gnupg2 is installed but the signature is not checked by the script; the sha256 pin alone is enforced.
- **note** `install.sh:15-16`: **x86_64-only.** The URL is hard-coded to the `ubuntu2404/...-ubuntu24.04.tar.gz` x86_64 build, and the pinned sha256 is that file's. There is no `uname -m` branch. On an arm64 container the hash check passes (it downloads the x86_64 file), then `swift --version` (`install.sh:35`) fails with an exec format error, or runs under binfmt emulation if Docker Desktop has it registered, and the build then cannot link a native binary. Official aarch64 tarballs exist (`ubuntu2404-aarch64/.../swift-6.4.2-RELEASE-ubuntu24.04-aarch64.tar.gz`, HTTP 200). To run natively on arm64, install.sh needs that URL and its own sha256, which is a change to the submission and needs a new review. Otherwise run with `SERVER_PLATFORM=linux/amd64`. build.sh itself handles both (`build.sh:34-37`: `-march=native` on x86_64, `-mcpu=native` on aarch64), and the io_uring syscall numbers 425-427 and struct offsets used are the same on both architectures.
- **note** `install.sh:9-13`: apt installs Swift's documented Ubuntu 24.04 runtime and build prerequisites (binutils, git, gnupg2, libcurl, libedit, libgcc/libstdc++-13-dev, libncurses, libpython3-dev, libsqlite3-0, libxml2, libz3, pkg-config, tzdata, unzip, zlib). That is more than this app strictly needs but is the upstream list. It also writes `/usr/local/bin/swift` and `/usr/local/bin/swiftc` as symlinks into /opt/swift.
- **note** `Package.swift:15`, `Sources/BTree/*`: SQLite is compiled with `SQLITE_PRIVATE` defined empty, so its internal B-tree functions get external linkage and Swift calls them directly (`SQLiteInternals.swift`). `Cursor.swift:204-211` hard-codes 3.54.1's `UnpackedRecord`/`Mem` offsets for a one-column seek key. These are used only after a startup self-check (`Reads.checkOneColumnSeeks`, `Reads.swift:215-242`) shows they count the same as SQLite's own two-column key. Reads fall back to SQL when `schemaMatches` fails. This is unusual but not hostile, and it stays inside SQLite's process memory.
- **note** `Package.swift:50,60,70,89`: every Swift module builds with `-Ounchecked -enforce-exclusivity=unchecked`, which removes `precondition`, array/Span bounds and overflow checks. The HTTP parser, JSON scanner, base64 and JWT code (`HTTP.swift`, `Codec.swift`, `Auth.swift`) parse network input with those checks compiled out, alongside raw pointer work in `Buffers.swift`, `IORing.swift` and `Cursor.swift`. I found no deliberate misuse, and the parsers do their own length checks (64 KiB of headers, a 1 MiB body, an 8-hex-digit chunk size, 64-deep JSON nesting, fixed stack buffers with explicit size checks before base64 decodes). A memory-safety bug would be reachable from network input, but only on the isolated bench network.
- **note**: complete syscall families, for the seccomp decision.
  - io_uring_setup, io_uring_enter and io_uring_register (FILES2 sparse, PBUF_RING, UNREGISTER_PBUF_RING) via `syscall(2)` (`IORing.swift:466,488`).
  - mmap of the ring fd, anonymous mmap for the buffer ring, munmap.
  - getrlimit, and setrlimit(RLIMIT_NOFILE) raising only the soft limit up to the inherited hard limit (`Sys.swift:46-54`).
  - socket, setsockopt (SO_REUSEADDR, SO_REUSEPORT, TCP_NODELAY, IPV6_V6ONLY), bind and listen: 8 SO_REUSEPORT listeners on HOST:PORT (`Sys.swift:62-92`, `Reactor.swift:83`).
  - eventfd read and write, write(2) to stderr, clock_gettime.
  - One extra thread via pthread_create, with pthread_setname_np and setpriority(nice 5) on that thread only (`Checkpointer.swift:63-71,119-130`).
  - SQLite's unix VFS on SQLITE_PATH and its -wal: open, pread, pwrite, fdatasync, fcntl locks, posix_fallocate (64 MiB chunks), ftruncate and stat. `PRAGMA mmap_size=0`. The checkpointer also opens SQLITE_PATH read-only for fdatasync (`Checkpointer.swift:24`).
  - No process spawning, no outbound connect, no Foundation or networking libraries, and no reads of /proc, /etc, $HOME, ~/.ssh, ~/.aws or docker.sock.
- **note** `Feed.swift:9-23,29`: env vars are SQLITE_PATH, JWT_SECRET, HOST and PORT, plus the optional integer tuning knobs RING_FILES, MAX_RINGS, RING_BUFFERS, PASS_BATCH, PASS_WINDOW_US, BTREE_READS and CHECKPOINT_THREAD (README:117-119). None is set by the harness. None changes file or network targets.
- **note** `Reads.swift:349`: `root()` interpolates a table name into SQL, but only the four constant names from `Reads.swift:45`, so there is no injection path. Request values are always bound as parameters (`Store.swift:236,250-252,273,279-280`).
- **note** `Auth.swift`: HS256 is implemented in-house (SHA-256 with the standard constants, HMAC with precomputed ipad/opad states). It compares signatures in constant time, requires `alg` HS256 and `exp`, honours `nbf`, and checks the signature before decoding the payload. The JWT secret is held in memory only and never logged.
- **note** `build.sh:20-24`: SQLite is fetched with `curl -fsSL --retry 3` into `.deps/`, verified with `sha256sum -c` before `unzip`, and only sqlite3.c and sqlite3.h are copied. build.sh runs as the unprivileged build user. `-march=native`/`-mcpu=native` and `-target-cpu` tie the binary to the build host's CPU, so build and run must be on the same machine. This is a portability issue, not a security one.

No blockers. No concerns above note level.
