# Security review: fsharp-uring-delneg

## Verdict
Safe to build and run. Nothing malicious or blocker-level was found. The server is a single-threaded F# (.NET 11) io_uring HTTP/1.1 server. It makes raw `io_uring_*` syscalls through `syscall(2)`, and it uses an unmodified, checksum-verified SQLite 3.54.1 amalgamation that build.sh compiles into a shared library and the server calls through P/Invoke. At runtime it reads only the four spec env vars plus optional tuning knobs, and `/proc/self/maps`. It touches only its listening sockets, accepted client sockets, two eventfds, and the SQLite file at SQLITE_PATH with its `-wal` sibling. With the `unix-excl` VFS there is no `-shm` file. It makes no outbound connections, spawns no processes and reads no credentials. The .NET SDK tarball's SHA-512 matches install.sh and Microsoft's release metadata. The SQLite zip's sha256 matches build.sh, and the sqlite3.c inside it matches the SHA3-256 that sqlite.org publishes for 3.54.1. The only lockfile dependency is FSharp.Core 11.0.101. Its lockfile hash matches the Microsoft-signed copy inside the verified SDK, and OSV reports nothing for it.

`seccomp: unconfined` is justified. start.sh runs `out/Server` with no flags. `Ring.fs:93-99` throws if `io_uring_setup` fails, and `Server.fs:1131-1138` rethrows when ring 0 can't be built, so the process dies at startup. There is no epoll or socket fallback, and no switch that turns one on. The server's io_uring use is limited to multishot accept into fixed descriptors, multishot receive with provided buffers, send, shutdown, close and async-cancel on its own listeners and accepted sockets, plus an 8-byte `READ` of its own checkpoint eventfd (`Server.fs:435`). It never uses OpenAt, Connect, Splice or file-write opcodes.

What "unconfined" exposes is the same as for other io_uring entries. The whole server container, including nginx and the entrypoint, runs without Docker's syscall filter. That widens the kernel attack surface, and io_uring has a history of local privilege-escalation CVEs. On Docker Desktop for Mac the exposed kernel is the LinuxKit VM's, not macOS. `no-new-privileges`, the default capability drop, resource limits and the non-root user still apply. That is acceptable for code that, as reviewed, does nothing hostile.

## Findings
- **note** `Server.fs:1131-1138`, `Ring.fs:93-103`: no fallback without io_uring. The server also requires `FEAT_SINGLE_MMAP` and `FEAT_EXT_ARG`, plus `SINGLE_ISSUER`/`DEFER_TASKRUN` setup flags (kernel 6.1+). The buffer-ring registration retries with `resv[0]=1` for a known Ubuntu 6.8 kernel bug, then falls back to `PROVIDE_BUFFERS` (`Ring.fs:159-171`, `Server.fs:235-244`). That fallback still uses io_uring.
- **note**: complete io_uring surface, for the seccomp decision. `io_uring_setup` (425), `io_uring_enter` (426) and `io_uring_register` (427: `REGISTER_FILES2` sparse, `REGISTER_PBUF_RING`). Opcodes used: ACCEPT (multishot, `FILE_INDEX_ALLOC`), RECV (multishot, fixed file, buffer select), SEND (`MSG_NOSIGNAL`), SHUTDOWN, CLOSE (fixed), ASYNC_CANCEL, PROVIDE_BUFFERS, and READ on the checkpoint eventfd only. `RecvInto`, `ShutdownClose` and `Mailbox` in Ring.fs are dead code.
- **note**: other syscall families. `mmap` is used only for the ring fd and anonymous memory. The server makes getrlimit/setrlimit(RLIMIT_NOFILE) calls that raise only the soft limit to the inherited hard limit (`Program.fs:54-58`), and `mlock` calls over its own mapped code (best effort, `Program.fs:20-40`). Sockets: `socket`, `setsockopt` (SO_REUSEADDR, SO_REUSEPORT, TCP_NODELAY, TCP_DEFER_ACCEPT), `bind` and `listen` on HOST:PORT (`Server.fs:1209-1231`). It creates two eventfds and one background thread, which drops its own priority to nice 19 (`Db.fs:815`). That thread opens SQLITE_PATH and `SQLITE_PATH-wal` read-only, only to call `posix_fadvise(DONTNEED)` on them (`Db.fs:833-851`). SQLite's unix VFS does open, pread, pwrite, fdatasync, fcntl locks and unlink on those files. No `connect`, no process spawning, and no reads of /etc, $HOME, ~/.ssh, ~/.aws or docker.sock.
- **note** `Program.fs:22`: reads `/proc/self/maps` (its own process) to choose which file-backed pages to `mlock`. Benign.
- **note** `Program.fs:43-47`: runtime env vars are SQLITE_PATH, JWT_SECRET, HOST and PORT. JWT_SECRET falls back to the challenge's published default `twelve-dollar-challenge` if unset. About 35 optional tuning variables are read as integers or flags, all with safe defaults (`Server.fs:23-46`, `Db.fs:29-36`, `Program.fs:60-65`, `Server.fs:317`). `VFS` picks a SQLite VFS by name, but only built-in or self-registered VFSes exist (`OMIT_LOAD_EXTENSION`). If HOST isn't an IP literal, `Dns.GetHostAddresses` resolves it (`Program.fs:51`). HOST is `0.0.0.0` in practice.
- **note** `Jwt.fs:20-30`: HMAC-SHA256 is built on OpenSSL's low-level `SHA256_Init/Update/Final` from the system `libcrypto.so.3`, through P/Invoke. The signature is checked before anything else in the token is parsed, and compared with `CryptographicOperations.FixedTimeEquals` (`Jwt.fs:155`). `alg` must be HS256, and `exp` is checked on every request. Correct.
- **note** `build.sh:23-30`, `Sqlite.fs`, `Db.fs`: build.sh compiles SQLite with `-DSQLITE_PRIVATE=`, which exports its internal `sqlite3Btree*` functions. The server reads B-tree cursors directly and builds `Mem`/`UnpackedRecord` search keys at hard-coded offsets (`Sqlite.fs:502-507`). There is heavy `unsafe` code: raw SQE/CQE writes, kernel-shared buffer rings, record decoding over page bytes, and VFS and page-cache shims written as managed delegates. I found no deliberate misuse. Network input is bounded: headers and body at most 16 KiB (`Server.fs:598,640,652`), token at most 4,096 bytes (`Jwt.fs:142`), and the JWT decode buffer is size-checked (`Jwt.fs:96-99`). The record decoder parses only bytes from the database file. A memory-safety bug would be reachable from network input, but only on the isolated bench network. At startup a self-test compares B-tree answers with SQL byte for byte and switches to SQL on any difference (`Db.fs:727-743`).
- **note** `build.sh:23`, `-march=native`: the SQLite library is tied to the build host's CPU. That is a portability issue, not a security one.
- **note** `src/packages.lock.json`, FSharp.Core: the lockfile's contentHash `/Us61HrX…8A9h4g==` matches the FSharp.Core 11.0.101 that ships inside the SDK (`sdk/11.0.100/FSharp/library-packs/`, signed by Microsoft Corporation). It does not match the nuget.org package of the same version (`XL1wfb0g…EXJVQ==`). That package is a different build of the same source commit (`dotnet/dotnet@297acf93`), Microsoft-signed with a NuGet.org repository countersignature. Both copies are genuine. The consequence: if restore takes the nuget.org copy instead of the SDK's offline one, locked mode fails the build with a hash error. The build fails closed; nothing different gets in.
- **note** `Server.fsproj:14`, `PublishReadyToRun`: the SDK fetches `Microsoft.NETCore.App.Crossgen2.linux-x64` 11.0.0 (and the matching `Microsoft.NETCore.App.Runtime` pack) from nuget.org at publish time. These implicit packs are not recorded in packages.lock.json. Their version is pinned by the SDK's BundledVersions.props (11.0.0), they are Microsoft-owned on the verified `Microsoft.*` prefix, and the .NET SDK verifies NuGet package signatures on Linux by default. Crossgen2 is a native compiler that runs during the build as the unprivileged build user. This is standard for any ReadyToRun .NET entry.
- **note** `build.sh:12`: telemetry is opted out (`DOTNET_CLI_TELEMETRY_OPTOUT=1`). `build.sh:35` stops the build servers afterwards.
- **note** `install.sh:11`: apt installs `ca-certificates curl unzip gcc libc6-dev libicu74 libssl3t64 zlib1g` with `--no-install-recommends`. That is all needed: gcc for SQLite, libssl for the HMAC, ICU for the SDK's tools. The app itself sets `InvariantGlobalization`.
- **note**, portability (not security): install.sh downloads only the `linux-x64` SDK, and `packages.lock.json` lists only the `net11.0/linux-x64` RID. On an arm64 host, build.sh's `--use-current-runtime` resolves to `linux-arm64`, and locked restore would reject the lockfile. Running it natively on aarch64 needs the changes listed under Downloads. Nothing in the F# code is x64-specific in practice. The io_uring syscall numbers (425-427), and the mmap, open, socket, errno and rlimit constants used, are the asm-generic values that arm64 shares. The `Mem`/`UnpackedRecord` offsets are documented "x86-64" but are LP64 layouts that aarch64 shares (inference, not verified on hardware).

No blockers. No concerns above note level.
